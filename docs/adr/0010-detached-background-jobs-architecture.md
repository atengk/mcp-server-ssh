# 0010. 受管脱机后台作业与用户态工作空间持久化架构

## 背景与决策 (Context & Decision)

当前 `ssh_exec` 采用同步阻塞等待模式。在长耗时任务（如内核编译、Docker 镜像构建、整库导出、复杂依赖安装等数分钟至数小时的命令）场景下，极易因 MCP 客户端请求超时或 SSH 底层物理连接波动/网络闪断导致通道关闭，使得远程前台进程接收到 `SIGHUP` 信号被迫终止。虽然持久终端 `ssh_session_*` 具备交互执行能力，但缺乏结构化的退出状态捕获、异步轮询与日志分段读取接口。

为此，我们决定设计并引入**受管脱机后台作业体系 (`ssh_job_*`)**：通过用户家目录下的隐式隔离工作空间 (`~/.mcp_jobs/<jobId>/`) 与标准的 `nohup` 解耦守护，实现长耗时作业的异步提交、进程存活监测、增量日志 Tail 与精确退出码闭环。

## 权衡考量 (Considered Options)

- **选项 1：依托系统临时目录 (`/tmp/.mcp_jobs/<jobId>/`)**。实现简单且无需关心残留，但多用户共享同一系统时存在权限碰撞漏洞；更关键的是，许多 Linux 发行版内置有定时清理机制（如 `systemd-tmpfiles-clean`、`tmpreaper`、`tmpwatch`），会在后台静默删除长时间运行作业的日志流与状态文件。
- **选项 2：强依赖远程第三方终端复用器 (`tmux` / `screen` / `systemd-run`)**。具有良好的会话隔离，但破坏了“零侵入直连”原则，在极简容器（如 Alpine、Distroless）或受限生产宿主机上极大概率未安装，导致服务可用性骤降。
- **选项 3：用户家目录隐式工作空间结合标准 Shell 守护（已采纳）**。每个作业独立创建 `~/.mcp_jobs/<jobId>/`，写入 `run.sh`，以 `nohup bash run.sh > stdout.log 2>&1 & echo $! > pid` 方式后台启动，并将退出码重定向至 `exit_code`。无需任何额外软件依赖，天生免疫多用户冲突与系统临时清理机制，并支持客户端通过 `ssh_job_clean` 或自动 TTL 清理过期产物。

## 后果与影响 (Consequences)

- 优势：
  - 即使 MCP 服务重启或 SSH 物理连接断开，远端脱机任务依然平稳运行不中断；
  - 提供细粒度的结构化接口（`ssh_job_start`、`ssh_job_status`、`ssh_job_logs`、`ssh_job_kill`、`ssh_job_clean`），降低 Agent 长时间自主运作的心智负担；
  - 100% 遵守无侵入直连架构，适用于任何标准 POSIX 兼容的 Linux/Unix 系统。
- 代价：
  - 需要在远程用户家目录下维护作业文件的读写与并发锁；
  - 需要设计合理的作业生命周期回收策略以防止磁盘无序堆积。
